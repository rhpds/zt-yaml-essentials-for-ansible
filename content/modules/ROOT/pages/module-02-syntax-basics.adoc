= YAML syntax basics - files, indentation, case sensitivity

== Learning Objectives

After completing this module, you will be able to:

* Identify the basic structure of a YAML file (documents, directives, spacing)
* Apply proper indentation rules when writing YAML
* Recognize how case sensitivity affects key names and values in YAML

== YAML file structure and document markers

Every YAML file is a collection of one or more documents. A YAML document starts with three dashes `---` called the document start marker. This marker is optional for single-document files but becomes required when a file contains multiple YAML documents.

Here is a simple single-document YAML file:

[source,yaml]
----
---
server: webserver
port: 80
enabled: true
----

The document start marker `---` signals to the YAML parser that a new document is beginning. While you can omit `---` in simple single-document files, including it is considered best practice. Red Hat Ansible Automation Platform Playbooks always start with `---` to clearly mark the beginning of the automation definition.

You can also use the optional document end marker `\...` to explicitly mark where a document ends. This is useful when you have multiple YAML documents in a single file:

[source,yaml]
----
---
server: webserver
port: 80
...
---
server: database
port: 5432
...
----

In this example, the file contains two separate YAML documents. The first defines a web server configuration, and the second defines a database configuration. Each document starts with `---` and ends with `\...`.

For Red Hat Ansible Automation Platform Playbooks, you typically work with single-document YAML files. Every Playbook starts with `---` and does not require the `\...` end marker.

== Indentation rules and the whitespace trap

YAML uses indentation to represent structure and hierarchy. This is one of YAML's defining characteristics — indentation is not just formatting, it defines the data structure itself.

*Critical rule:* YAML requires spaces for indentation. Tabs are forbidden. If you use tabs, the YAML parser will reject your file with an error.

Most YAML files use two spaces per indentation level. This is the standard for Red Hat Ansible Automation Platform Playbooks. Here is an example with proper indentation:

[source,yaml]
----
---
server:
  name: webserver
  port: 80
  config:
    ssl: true
    timeout: 30
----

In this example:
- `server` is at the root level (no indentation)
- `name`, `port`, and `config` are indented 2 spaces, making them children of `server`
- `ssl` and `timeout` are indented 4 spaces total (2 more than `config`), making them children of `config`

The indentation level determines which keys belong to which parent. If you change the indentation, you change the structure.

*The whitespace trap:*

Here is a common mistake that catches many people when they start writing YAML:

[source,yaml]
----
---
- name: Configure Apache
  package: httpd
  service: httpd
----

This YAML is syntactically valid, but it does not create the structure you might expect. The keys `package` and `service` are not separate items — they are both treated as the value of the `name` key.

To create a list item with multiple keys, you need to indent the keys under the list item:

[source,yaml]
----
---
- name: Configure Apache
  package:
    name: httpd
    state: present
  service:
    name: httpd
    state: started
----

The indentation tells the YAML parser that `package` and `service` are keys at the same level under the list item, each with their own nested key-value pairs.

Indentation is not just whitespace — it defines the data structure. Get the indentation wrong, and you change the meaning of your YAML file.

== Case sensitivity and comments

YAML is case-sensitive. This means `Name`, `name`, and `NAME` are three completely different keys. The YAML parser treats them as distinct.

Consider this example:

[source,yaml]
----
---
server:
  Name: webserver
  name: database
  NAME: cache
----

This YAML defines three separate keys under `server`: `Name`, `name`, and `NAME`. Each has a different value. This is valid YAML, but it is confusing and likely not what you intended.

When writing Red Hat Ansible Automation Platform Playbooks, follow the convention of using lowercase keys. Ansible modules, task attributes, and playbook keywords are all lowercase. Consistency matters.

*Comments in YAML:*

YAML supports comments using the `#` character. Everything after `#` on a line is treated as a comment and ignored by the parser.

[source,yaml]
----
---
# This is a comment explaining the server configuration
server:
  name: webserver  # This is an inline comment
  port: 80
  enabled: true
----

Comments are useful for documenting your YAML files. They explain why certain values are set, provide context for other team members, and help you remember your decisions when you revisit the file later.

Use comments generously in your Red Hat Ansible Automation Platform Playbooks. Automation content is read many times by many people. Clear comments make collaboration easier.

== Hands-on: Write your first valid YAML file

Now that you understand the syntax rules, practice writing a valid YAML file.

. Create and open a new file called `syntax-practice.yml` in VS Code:
+
* Click *File > New File* in the VS Code menu
* Save the file as `syntax-practice.yml` in your workspace directory
* Alternatively, right-click in the VS Code Explorer pane and select *New File*, then name it `syntax-practice.yml`

. Add the document start marker `---` at the top of the file.

. Add three key-value pairs with proper indentation (2 spaces per level):
+
[source,yaml]
----
---
environment: production
region: us-east-1
instances: 5
----

. Add a comment explaining what this configuration represents:
+
[source,yaml]
----
---
# Production environment configuration
environment: production
region: us-east-1
instances: 5
----

. Save the file and observe the syntax highlighting in VS Code. If the YAML is valid, VS Code will highlight the keys, values, and comments in distinct colors. If there is a syntax error, you will see red underlines or warnings.

=== Verify

Confirm that your `syntax-practice.yml` file contains:

* The document start marker `---` at the top
* At least three key-value pairs with proper indentation (2 spaces)
* At least one comment starting with `#`
* Valid syntax as indicated by VS Code syntax highlighting (no red underlines or error markers)

If VS Code shows errors, check your indentation. Make sure you are using spaces, not tabs. Verify that all keys are properly aligned.

== Conclusion

YAML files use the document start marker `---` to signal the beginning of a document. This marker is standard in Red Hat Ansible Automation Platform Playbooks and considered best practice for all YAML files.

Indentation defines structure in YAML. You must use spaces, not tabs. The indentation level determines which keys belong to which parent. Changing indentation changes the data structure itself.

YAML is case-sensitive. Keys like `name`, `Name`, and `NAME` are treated as completely different. Stick to lowercase keys when writing Red Hat Ansible Automation Platform content to maintain consistency with Ansible conventions.

Use comments starting with `#` to document your YAML files. Comments help others understand your automation content and make collaboration easier.
