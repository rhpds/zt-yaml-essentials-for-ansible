= YAML data types - dictionaries, lists, scalars, comments

== Learning Objectives

After completing this module, you will be able to:

* Write YAML scalars (strings, numbers, booleans) following proper syntax
* Create YAML lists using both block style and inline flow style
* Define YAML dictionaries (key-value pairs) with correct indentation
* Add comments to YAML files for documentation purposes
* Combine dictionaries, lists, and scalars to represent Ansible playbook structures

== Scalars: strings, numbers, and booleans

Scalars are the simplest data type in YAML. A scalar is a single value — not a collection, not a structure, just one piece of data.

YAML supports three basic types of scalars:

*Strings:* Text values, either quoted or unquoted. Most simple strings do not require quotes:

[source,yaml]
----
server_name: webserver
description: Apache web server for production
----

However, you should use quotes when the string contains special characters or when you need to force a value to be treated as a string:

[source,yaml]
----
version: "2.0"  # Without quotes, this becomes a number
special: "value: with colons"  # Quotes required because of the colon
----

*Numbers:* Integer or floating-point values, written without quotes:

[source,yaml]
----
port: 80
timeout: 30
cpu_load: 2.5
----

*Booleans:* True or false values. YAML accepts several forms:

[source,yaml]
----
enabled: true
debug: false
ssl_verify: yes
auto_start: no
----

The values `true`, `false`, `yes`, and `no` are all recognized as booleans. Red Hat Ansible Automation Platform Playbooks typically use `true` and `false` for consistency with most programming languages.

*When to use quotes:*

Quotes force YAML to treat a value as a string. Use quotes when:

- The value looks like a number but should be treated as text: `version: "2.0"`
- The value contains special characters like colons: `message: "Error: connection failed"`
- You want to preserve leading zeros: `zip_code: "02134"`

Without quotes in these cases, YAML might interpret the value incorrectly.

== Lists: block and flow styles

Lists are ordered collections of items. Each item in a list can be any YAML data type — scalars, dictionaries, or even other lists.

YAML provides two ways to write lists: block style and flow style.

*Block style lists* use a dash followed by a space to mark each item. Each item appears on its own line:

[source,yaml]
----
packages:
  - httpd
  - firewalld
  - vim-enhanced
----

This list contains three string values: `httpd`, `firewalld`, and `vim-enhanced`. Block style is the preferred format for Red Hat Ansible Automation Platform Playbooks because it is easy to read and modify.

*Flow style lists* use square brackets and commas, similar to JSON:

[source,yaml]
----
packages: [httpd, firewalld, vim-enhanced]
----

Flow style is compact but harder to read when lists contain many items or complex values. Use flow style sparingly.

*Lists in Ansible Playbooks:*

Red Hat Ansible Automation Platform tasks are lists of dictionaries. Each task is a list item (marked with a dash), and each item is a dictionary containing the task definition:

[source,yaml]
----
tasks:
  - name: Install Apache
    ansible.builtin.package:
      name: httpd
      state: present

  - name: Start Apache service
    ansible.builtin.service:
      name: httpd
      state: started
----

Notice how each task starts with a dash. The `tasks` key contains a list of two items. Each item is a dictionary with keys like `name`, `ansible.builtin.package`, and `ansible.builtin.service`.

== Dictionaries: key-value pairs and nesting

Dictionaries (also called mappings or hashes) are collections of key-value pairs. Each key maps to a value. Keys must be unique within their scope.

*Block style dictionaries* use a key, followed by a colon and a space, then the value:

[source,yaml]
----
server:
  name: webserver
  port: 80
  enabled: true
----

In this example, `server` is a key whose value is another dictionary. The nested dictionary contains three keys: `name`, `port`, and `enabled`. Indentation defines the nesting — the nested keys are indented 2 spaces under `server`.

*Flow style dictionaries* use curly braces and commas:

[source,yaml]
----
server: {name: webserver, port: 80, enabled: true}
----

Flow style is compact but harder to read for complex structures. Block style is preferred for Red Hat Ansible Automation Platform content.

*Nesting dictionaries:*

You can nest dictionaries multiple levels deep. Each level is indented 2 more spaces:

[source,yaml]
----
webserver:
  apache:
    package: httpd
    service: httpd
    config:
      port: 80
      ssl: true
      document_root: /var/www/html
----

In this example:

- `webserver` is the root key
- `apache` is a key nested under `webserver` (indented 2 spaces)
- `package`, `service`, and `config` are keys nested under `apache` (indented 4 spaces)
- `port`, `ssl`, and `document_root` are keys nested under `config` (indented 6 spaces)

The indentation level determines the parent-child relationships. Change the indentation, and you change the structure.

*Dictionary keys must be unique:*

Within the same scope, you cannot repeat a key. This is invalid:

[source,yaml]
----
server:
  name: webserver
  name: database  # Error: duplicate key
----

The YAML parser will reject this or silently use only the last value for `name`. Avoid duplicate keys.

== Multi-line strings

Sometimes you need to include long text or multi-line content in your YAML files. YAML provides two block scalar operators to handle multi-line strings: the pipe `|` and the greater-than symbol `>`.

*Pipe operator `|` — preserves newlines:*

The pipe operator preserves all newlines exactly as written. Use this for scripts, configuration files, or any content where line breaks matter:

[source,yaml]
----
script: |
  #!/bin/bash
  echo "Starting deployment"
  systemctl restart httpd
  echo "Deployment complete"
----

When YAML parses this, the value of `script` will include all four lines with their newlines preserved. This is perfect for shell scripts or multi-line configuration content.

*Greater-than operator `>` — folds newlines:*

The greater-than operator folds newlines into spaces, creating a single long string. Use this for long descriptions or paragraphs:

[source,yaml]
----
description: >
  This is a very long description that spans multiple lines
  in the YAML file but will be treated as a single line
  with spaces instead of newlines when parsed.
----

The parser converts all the newlines to spaces, resulting in: `"This is a very long description that spans multiple lines in the YAML file but will be treated as a single line with spaces instead of newlines when parsed."`

*Multi-line strings in Ansible tasks:*

The pipe operator is commonly used in Red Hat Ansible Automation Platform tasks when running shell commands:

[source,yaml]
----
- name: Run deployment script
  ansible.builtin.shell: |
    cd /opt/app
    ./deploy.sh
    systemctl restart app-service
----

This preserves the line breaks, allowing you to run multiple commands in sequence.

. Add the document start marker `---` at the top of the file.

. Write a scalar string value:

  - redis

  config:
    port: 5432
    max_connections: 100

. Add a multi-line string using the pipe operator:
+

---
application_name: inventory-management

  - postgresql

  engine: postgresql

== Conclusion

YAML provides three core data types: scalars, lists, and dictionaries. Scalars are single values like strings, numbers, or booleans. Lists are ordered collections marked with dashes in block style or brackets in flow style. Dictionaries are key-value pairs, with nested dictionaries indented to show hierarchy.

Multi-line strings use the pipe `|` operator to preserve newlines or the greater-than `>` operator to fold newlines into spaces. These operators are essential for including scripts and long text in YAML files.

Red Hat Ansible Automation Platform Playbooks combine all three data types. Tasks are lists of dictionaries. Each task dictionary contains scalar values, nested dictionaries for module parameters, and sometimes lists of items to process. Understanding how to combine these data types is critical for writing effective automation content.
