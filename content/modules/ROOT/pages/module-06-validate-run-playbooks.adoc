= Validate and run Ansible playbooks

== Learning Objectives

After completing this module, you will be able to:

* Apply the two-step validation workflow: yamllint first, then Ansible syntax check
* Understand the difference between YAML syntax validation and Ansible-specific validation
* Validate a real Ansible playbook for both YAML correctness and Ansible structure
* Optionally run an Ansible playbook and observe successful execution

== The two-step validation workflow

Validating an Ansible playbook requires two distinct checks. Each check catches different types of errors because each tool validates a different aspect of the file.

*Step 1: yamllint (YAML syntax validation)*

yamllint validates pure YAML syntax. It checks:

- Indentation and spacing (tabs vs spaces, consistent indentation levels)
- YAML data types (strings, numbers, booleans, lists, dictionaries)
- Document markers (`---` at the start)
- YAML best practices (trailing spaces, line length, key naming)

yamllint is language-agnostic. It validates YAML structure without understanding Ansible-specific keywords, modules, or playbook semantics. You use yamllint for Kubernetes manifests, Docker Compose files, CI/CD pipelines, and Ansible playbooks. It validates the YAML container, not the content inside the container.

*Step 2: ansible-playbook --syntax-check (Ansible structure validation)*

ansible-playbook --syntax-check validates Ansible-specific structure. It checks:

- Valid Ansible module names (ansible.builtin.package, not packag)
- Required module parameters (name is required for ansible.builtin.package)
- Variable syntax ({{ variable_name }} format)
- Task structure (tasks must have a name and a module)
- Playbook structure (plays must have hosts and tasks)

ansible-playbook --syntax-check parses the YAML file as an Ansible playbook. It understands Ansible keywords like `hosts`, `tasks`, `become`, and `vars`. It validates that the playbook is structurally correct according to Ansible rules.

*Why both checks are needed:*

A file can pass yamllint but fail Ansible syntax check. The file is valid YAML but invalid Ansible. For example:

[source,yaml]
----
---
- hosts: all
  tasks:
    - name: Install Apache
      packag:  # typo: should be 'package'
        name: httpd
        state: present
----

This YAML is syntactically correct. The indentation is proper, the data types are valid, and the structure is valid YAML. yamllint will pass this file.

But the Ansible syntax check will fail because `packag` is not a valid Ansible module. Ansible cannot parse the task because it does not recognize the module name.

*The professional validation workflow:*

Always run yamllint first. If yamllint fails, fix YAML syntax errors before running Ansible syntax check. There is no value in checking Ansible structure if the YAML syntax is broken. Ansible cannot parse invalid YAML.

Once yamllint passes, run ansible-playbook --syntax-check. This confirms that the YAML structure is correct and the Ansible content is valid.

== Hands-on: Validate apache-playbook.yml

The file `apache-playbook.yml` is a real Ansible playbook that installs and configures the Apache web server. You will validate this playbook using the two-step workflow.

. Open the file `apache-playbook.yml` in VS Code from the lab environment.

. Review the playbook structure. Observe the following elements:
+
- The `hosts` key specifies which systems the playbook targets
- The `become` key indicates that tasks run with elevated privileges
- The `tasks` section contains a list of Ansible tasks
- Each task has a `name` (description) and a module (such as `ansible.builtin.package` or `ansible.builtin.service`)
- Module parameters (such as `name`, `state`, `enabled`) define what the module should do
+
This is a typical Red Hat Ansible Automation Platform playbook. You will encounter this structure in production environments.

. Run yamllint on the playbook to validate YAML syntax:
+
[source,bash,role="execute"]
----
yamllint apache-playbook.yml
----
+
If yamllint produces no output, the YAML syntax is valid. The file passes all YAML structure and style checks.
+
If yamllint reports errors, the output will show the filename, line number, column number, and error description. Use the error message to navigate to the problem location in VS Code. Fix the error using the skills from Module 5 (replace tabs with spaces, fix indentation, remove trailing spaces, add missing colons or spaces). Save the file and re-run yamllint until it produces no output.

. Once yamllint passes, run the Ansible syntax check:
+
[source,bash,role="execute"]
----
ansible-playbook --syntax-check apache-playbook.yml
----
+
*If the playbook is valid:* ansible-playbook prints:
+
[source,text]
----
playbook: apache-playbook.yml
----
+
This output confirms that the playbook is syntactically correct according to Ansible rules. No errors were found. The playbook is ready to run.
+
*If the playbook is invalid:* ansible-playbook prints an error message showing the line number and the Ansible-specific issue. Common Ansible errors that yamllint does not catch include:
+
- *Module name typos:* `ansible.builtin.packag` instead of `ansible.builtin.package`
- *Missing required parameters:* A module requires the `name` parameter but the playbook does not provide it
- *Invalid variable syntax:* `{ variable_name }` instead of `{{ variable_name }}`
- *Incorrect task structure:* A task is missing the `name` key or the module key

. If the Ansible syntax check fails, read the error message carefully. Navigate to the line number indicated in the error. Fix the issue based on the error description. Save the file.

. Re-run both validation steps after making changes:
+
[source,bash,role="execute"]
----
yamllint apache-playbook.yml
----
+
[source,bash,role="execute"]
----
ansible-playbook --syntax-check apache-playbook.yml
----
+
Repeat this cycle until both checks pass.

=== Verify

Confirm that running `yamllint apache-playbook.yml` produces no output and running `ansible-playbook --syntax-check apache-playbook.yml` prints `playbook: apache-playbook.yml` without errors.

If yamllint reports errors, fix YAML syntax issues first before proceeding to the Ansible syntax check. If the Ansible syntax check fails, read the error message carefully and verify that:

* All module names are spelled correctly (ansible.builtin.package, ansible.builtin.service)
* All required module parameters are present (name, state)
* All tasks have a name key and a module key
* Variable syntax uses double curly braces: `{{ variable_name }}`

== Optional: Run the playbook and observe results

Once both validation checks pass, the playbook is ready to run. Running the playbook executes each task in sequence and makes changes to the target systems.

This step is optional. If you choose to run the playbook, you will see Ansible output showing each task executing and the results.

. Run the playbook:
+
[source,bash,role="execute"]
----
ansible-playbook apache-playbook.yml
----
+
Ansible will connect to the target hosts specified in the playbook and execute each task. You will see output showing:
+
- *PLAY:* The name of the play (the group of tasks targeting specific hosts)
- *TASK:* The name of each task as it executes
- *CHANGED/OK:* Whether the task made changes to the system (CHANGED) or found the system already in the desired state (OK)
- *PLAY RECAP:* A summary showing how many tasks succeeded, failed, or changed state on each host

. Observe the PLAY RECAP at the end of the output. The recap shows:
+
[source,text]
----
PLAY RECAP *********************************************************************
hostname                   : ok=X    changed=Y   unreachable=0    failed=0
----
+
This summary tells you:
+
- *ok:* Number of tasks that succeeded
- *changed:* Number of tasks that made changes to the system
- *unreachable:* Number of hosts that Ansible could not connect to (should be 0)
- *failed:* Number of tasks that failed (should be 0)
+
If `failed=0`, the playbook ran successfully. All tasks completed without errors.

. Verify that Apache is installed and running (optional). You can confirm the playbook's work by checking that the Apache web server is active:
+
[source,bash,role="execute"]
----
curl localhost
----
+
You should see the default Apache welcome page HTML output. This confirms that Apache was installed, started, and is serving content.

=== Verify

If you chose to run the playbook, confirm that the PLAY RECAP shows `failed=0`. This indicates that all tasks completed successfully.

If any tasks failed, read the error output from Ansible. The error message will indicate which task failed and why. Common runtime errors include:

* Network connectivity issues (Ansible cannot reach the target hosts)
* Permission errors (tasks require elevated privileges but `become` is not set)
* Missing dependencies (a package is not available in the configured repositories)

== Conclusion

Validating an Ansible playbook requires two distinct checks. yamllint validates pure YAML syntax. It checks indentation, spacing, data types, and YAML best practices. ansible-playbook --syntax-check validates Ansible-specific structure. It checks module names, required parameters, variable syntax, and playbook structure.

A file can pass yamllint but fail Ansible syntax check because yamllint is language-agnostic. It validates the YAML container without understanding the Ansible content inside the container. The Ansible syntax check parses the file as an Ansible playbook and validates Ansible semantics.

Always run yamllint first. If yamllint fails, fix YAML syntax errors before running the Ansible syntax check. There is no value in checking Ansible structure if the YAML syntax is broken. Once yamllint passes, run ansible-playbook --syntax-check to confirm that the Ansible content is valid.

This two-step validation workflow is used by professionals across all YAML-based automation platforms. yamllint is universal (Kubernetes, Docker Compose, CI/CD pipelines, Ansible). Application-specific syntax checks (kubectl, docker-compose validate, ansible-playbook --syntax-check) validate the content inside the YAML container.

You have now validated a real Ansible playbook using the two-step workflow. You understand the difference between YAML syntax validation and Ansible-specific validation. You can apply this workflow to any Ansible playbook to ensure it is syntactically correct and ready to run.
